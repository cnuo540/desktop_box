## 三、日常循环：改代码 → 编译 → 测试 → 本地部署

### 1. 编译

```powershell
cd <仓库根>
dotnet build src\DesktopBox\DesktopBox.csproj -c Release
```

产物在 `src\DesktopBox\bin\Release\net8.0-windows\DesktopBox.dll`。

> **重要认知**：主程序的业务逻辑**全部在这一个 DLL 里**（XAML 会被编成 BAML 嵌进去）。`DesktopBox.exe` 只是个 176 KB 的 apphost 启动器。
> 所以：**只改了 C#/XAML → 只需要替换这个 DLL，不用重新装**。下面的部署流程就是基于这一点。

### 2. 跑测试

```powershell
dotnet test src\DesktopBox.Tests\DesktopBox.Tests.csproj -c Release
```

CI 里也是这么跑的。如果 `dotnet test` 在你机器上起不来（我遇到过环境导致的 NuGet / TEMP 问题），可以在脚本里补上环境变量再试：

```powershell
$env:ProgramFiles = "C:\Program Files"
${env:ProgramFiles(x86)} = "C:\Program Files (x86)"
$env:ProgramData  = "C:\ProgramData"
```

> **测试里有大量「守卫测试」**：它们不跑功能，而是 `File.ReadAllText()` 读源码后 `Should().Contain(...)` 断言某些关键字还在。
> 这类测试的用途是**防止架构被改回去**。例如 `ShellBehaviorTests` 会锁住「盒子必须是 `WS_POPUP` 顶层窗口」；`BoxCollapseTests` 会锁住设置面板里的若干资源键。
> 所以：**删掉某个功能时，先搜一遍 Tests 目录里有没有断言它的地方**，否则会莫名其妙红。

### 3. 本地部署（替换正在跑的版本）

安装目录：`C:\Users\<你>\AppData\Local\Programs\DesktopBox\`

```powershell
# 1) 退出运行中的实例（托盘右键 → 退出，或杀进程）
Stop-Process -Name DesktopBox -Force -ErrorAction SilentlyContinue

# 2) 先备份要替换的 DLL（回退点）
Copy-Item "$inst\DesktopBox.dll" "$inst\DesktopBox.dll.before-change"

# 3) 换上新 DLL
Copy-Item "<build 输出>\DesktopBox.dll" "$inst\DesktopBox.dll" -Force

# 4) 启动
Start-Process "$inst\DesktopBox.exe"
```

**两个要点：**

- 如果正在跑的那个实例是**管理员权限**启动的，普通权限的 shell 杀不掉它 → 请从托盘退出。
- 要**换整个发布形态**（比如从单文件换成多文件自包含）时，不要只换 DLL，要整目录覆盖。

### 4. 看日志

```
C:\Users\<你>\AppData\Local\Programs\DesktopBox\logs\app.log
```

日志里能读到的有用信息：

- `[v1.7.36]` —— 当前跑的版本号（跟着 csproj 走）
- `App.Startup ==== start v1.7.36 pid=... DataDir=... ====`
- `DesktopHost.Ensure 已建窗 header=... parent=0x0` —— **`parent=0x0` 表示盒子是顶层窗口（v1.7.36 的方案）**；如果这里是具体的父句柄，说明跑的是子窗口方案的旧版本
- `DesktopLayer.MenuResult ... shown=True appearedMs=...` —— **这是顶层窗口版特有的字段**，可以用来判断当前跑的是哪一版

### 5. 版本号

**只有一个地方要改**：`src/DesktopBox\DesktopBox.csproj` 里的 `<Version>`。

```xml
<Version>1.7.36</Version>
```

改完之后，这些地方会自动跟着变：

- 程序集的 FileVersion / ProductVersion
- 日志前缀 `[v1.7.36]`
- 设置面板底部的版本号（它从程序集读，不写死）
- 安装包的 `FileVersion`
- `release.ps1` 的 tag 名（`v1.7.36`）

## 四、四种发布形态（以及为什么安装包用「多文件自包含」）

同一个项目，用不同的 publish 参数可以得到四种产物。**实测过**：

| 形态 | 参数要点 | 体积 | 冷启动 | 热启动 | 用途 |
|---|---|---|---|---|---|
| **单文件 + 压缩**（旧绿色版） | `PublishSingleFile=true` + `EnableCompressionInSingleFile=true` + `IncludeNativeLibrariesForSelfExtract=true` | ~74 MB | 慢（要解压到 `%TEMP%`） | ~850 ms | 早期绿色版；**已不再用于安装包** |
| **多文件自包含**（当前安装包用） | 三个参数全 `false`，`SelfContained=true` + `-r win-x64` | 167 MB（758 个文件） | **~8.3 s** | ~850 ms | **安装包的载荷** |
| 框架依赖 | `SelfContained=false` | ~170 KB 的 exe | — | ~832 ms | 只适合用户已装 .NET 8 的场景 |
| 绿色版 zip | 单文件 + helper 打 zip | 74 MB + 162 KB | 同单文件 | 同单文件 | `release.ps1` 的产出 |

### 关键结论（本机实测，2026-10-16）

1. **三种形态的热启动基本相同，都在 0.85 秒左右**。差别只在冷启动。
2. 单文件那代**冷启动最慢**，因为它要把 71 MB 解压到 `%TEMP%\.net\`。
3. 更糟的是：**如果系统的清理工具把 `%TEMP%` 清了，每次开机都要再付一次解压的钱**。
4. **多文件自包含不解压**，所有 DLL 直接躺在安装目录里被加载 —— 这就是安装包改用它的原因。

> 「开机自启速度」的收益也来自这里：DesktopBox 是开机自启的常驻程序，用多文件自包含可以**省掉开机时那次解压**。
> （如果你要极致的开机速度，下一档是「框架依赖 + 用户装 .NET」，热启动略快一点，但代价是要求用户机器上有 .NET 8 —— 对一个桌面整理工具来说不划算。）

## 五、制作安装包（自包含多文件 + UAC 启动器）

### 一句话命令

```powershell
cd <仓库根>
powershell -ExecutionPolicy Bypass -NoProfile -File .\scripts\build-installer.ps1
```

产出：`release\DesktopBoxSetup.exe`（v1.7.36 约 **49.6 MB**）。

### 四步流水线（脚本内部做的事）

| 步骤 | 做什么 | 产物 |
|---|---|---|
| `[1]` | `dotnet publish` **多文件自包含** | `publish-installer\`（167 MB / 758 文件） |
| `[2]` | 用 MSVC 编译原生右键菜单 helper | `publish-installer\DesktopBox.ShellMenu.exe` |
| `[3]` | ISCC 编译 `DesktopBox.iss` | `release\DesktopBoxSetupCore.exe`（约 49.6 MB，Inno 核心包） |
| `[4]` | 用 MSVC 编译 UAC 启动器，把核心包嵌进去 | `release\DesktopBoxSetup.exe`（最终交付物），**然后删掉核心包** |

如果 CI 里已经单独 publish 过了，可以跳过第 1 步：`-SkipPublish`（`build.yml` 就是这么用的）。

> **脚本里的一个关键约束**：第 1 步**必须先清空 `publish-installer\`**。
> 因为 `DesktopBox.iss` 用的是通配符 `publish-installer\*` 打包，残留文件（甚至一次冒烟测试留下的 `boxes.json` 用户数据）会被一起打进安装包里。

### 产物长什么样：外壳 + 内嵌核心

```
DesktopBoxSetup.exe  (49.6 MB)        ← 用户双击的就是它
├─ PE 资源 RT_MANIFEST:
│    requestedExecutionLevel level="requireAdministrator"   ← 关键
├─ PE 资源 RT_RCDATA id=101:
│    DesktopBoxSetupCore.exe (49.4 MB)                      ← 原 Inno 安装程序
└─ 运行时行为: UAC 提权 → 把核心包解到 %TEMP% → 运行它 → 等它退出 → 删除临时文件
     参数（/VERYSILENT 等）原样转发给核心包
```

外壳的源码：`src\DesktopBox.InstallerBootstrapper\`

- `DesktopBoxSetupBootstrap.cpp` —— 解包 / 运行 / 等待 / 清理
- `bootstrapper.manifest` —— 一行 `level="requireAdministrator"`，整件事的关键
- `DesktopBoxSetupBootstrap.rc` —— 图标 + `101 RCDATA "release\DesktopBoxSetupCore.exe"` + `1 24 "bootstrapper.manifest"` + 版本资源

### 为什么需要这层外壳（这个坑值得单独记）

**现象**：双击安装包报
```
Setup was unable to create the directory
C:\Users\...\AppData\Local\Temp\is-XXXX.tmp. Error 5: 拒绝访问
```
但**右键 → 以管理员身份运行却装得干干净净**。

**根因**：Inno 的**启动器**（Setup Launcher）会在**请求提权之前**，先去 `%TEMP%` 创建解包目录 `is-*.tmp`。
在拦「安装程序这类进程写系统位置」的机器上，这一步在普通权限下就被拒了，于是**根本走不到弹 UAC 那一步**。而右键提权时，进程从出生就是管理员，同一个目录就建得成功。

**结论**：缺的不是权限，是**次序** —— 必须先提权，再写临时目录。

**两个走过的弯路**（不要再试）：

1. 设 `PrivilegesRequired=admin`（让 Inno 自己弹 UAC）→ **无效**。那个设置管的是「启动器解完包、进入真正安装阶段之后」，够不到启动器自己的初始化。
2. 改回 `PrivilegesRequired=lowest` → 同样无效。

> `DesktopBox.iss` 里最终保留了 `PrivilegesRequired=admin` + `PrivilegesRequiredOverridesAllowed=commandline`，是为了 `[Run]` 里的 `runasoriginaluser` 能生效（装完自动启动的主程序必须以**原用户**身份运行，否则桌面层和 explorer 的交互会全乱）。**但真正解决双击装不上的是外壳**，不是这个设置。

### 验证安装包（不用真机盲测）

用 `pefile` 读 PE 资源，两件事必须都在：

```python
import pefile, hashlib
pe = pefile.PE("release/DesktopBoxSetup.exe", fast_load=True)
pe.parse_data_directories()
# 1) RT_MANIFEST (type 24) 里必须有 requireAdministrator
# 2) RT_RCDATA (type 10) 里必须有 id=101，大小约 49 MB（内嵌的核心包）
```

另外核对 `FileVersion` 应为 `1.7.36.0`、`FileDescription` 应为 `DesktopBox Setup`（UAC 弹窗里显示的就是这个名字）。

| | 本地 | CI (`build.yml`) |
|---|---|---|
| 触发 | 手动 | push 到 `main` / push 标签 `v*` |

## 六、开机自启

实现：`src\DesktopBox\Services\StartupService.cs`

| 项 | 值 |
|---|---|
| 注册表键 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` |
| 值名 | `DesktopBox` |
| 值内容 | `"完整路径\DesktopBox.exe"`（带引号，路径含空格时必需） |

路径解析策略（`ResolveExecutablePath()`）：**优先取进程真实的镜像路径**（这样对单文件发布也正确），取不到再退到 `AppContext.BaseDirectory` 下找 `DesktopBox.exe`。

开关入口在设置面板：`MainWindow` → 托盘菜单 → 「设置」→ 「开机自启」。

**和启动速度的关系**：因为 DesktopBox 是开机自启的常驻程序，安装包改成「多文件自包含」之后，**开机时不再需要把 71 MB 解压到 `%TEMP%`**（这是单文件那代最贵的一步）。详见第四章的实测数据。

## 七、核心架构决策：窗口为什么必须是顶层

这是 v1.7.36 最重要的一次架构变更，换电脑后如果你看到「子窗口」相关的老代码/老提交，需要知道这是**故意换过来的**。

### 权衡

| 方案 | 优点 | 代价 |
|---|---|---|
| 盒子/桌面层/覆盖层**挂成桌面宿主的子窗口**（早期方案） | z 序天然稳定：永远压在壁纸之上、普通窗口之下 | **子窗口与父窗口之间不做 alpha 混合**，透明像素会被合成为**不透明黑**。加不加 `WS_EX_LAYERED`、`UsesPerPixelOpacity` 取 true 还是 false，结果都一样 |
| **全部改成顶层窗口**（v1.7.36 采用） | 真透明：逐像素 alpha 生效，半透明底真的透出壁纸，圆角也能靠区域裁掉，没有黑角 | z 序随点击变化：**点别的窗口会盖住盒子**，点盒子它才抬起来（代码里已注明「已接受」） |

### 自校验探针的实测数据（决定性的证据）

做了一个对照探针：父窗口铺纯绿底，被测窗口是子窗口。结果 —— **子窗口的透明像素被合成成不透明黑，实测占窗口区域 97%（正确时应该透出壁纸 95%）**。
另外试过全部失败：`DwmExtendFrameIntoClientArea`（hr=0x80070057）、`LWA_COLORKEY`（err=87）。

所以子窗口这条路**实测走不通**，不是没调好参数。

### 三种窗口在 v1.7.36 里的挂法

| 窗口 | 样式 | z 序策略 | 关键点 |
|---|---|---|---|
| `BoxWindow` | `WS_POPUP \| WS_VISIBLE` + `WS_EX_TOOLWINDOW \| WS_EX_LAYERED \| WS_EX_NOACTIVATE`，`UsesPerPixelOpacity = true` | **非置顶**（`HWND_NOTOPMOST`）。不能置顶：置顶会压住普通窗口 | `EnsureVisibleOnDesktopHost(above)` 的形参是「盒子该排在谁上面」（桌面层的句柄），不是父窗口 |
| `DesktopLayerWindow` | 同上 | 排到 `HWND_BOTTOM`（壁纸之上、其余一切之下） | 窗口区域被裁成**图标矩形并集**（`SetWindowRgn` + `RGN_OR`），图标之间的空白归 explorer，所以右键桌面菜单、从资源管理器拖文件到桌面都不受影响 |
| `DesktopDropOverlay` | 同上 | `HWND_TOPMOST`（只在拖拽期间存在，不影响平时） | 盒子位置挖洞，保证拖到盒子上的落点归盒子 |

### 判断「当前跑的是哪一版」的两个日志判据

```
DesktopHost.Ensure ... parent=0x0        ← 0x0 = 顶层窗口（v1.7.36）；非 0 = 子窗口方案
DesktopLayer.MenuResult ... shown=True appearedMs=...   ← 顶层窗口版才有这个字段
```

### 盒子背景不透明度

- 模型：`AppSettings.BoxOpacity`（0.1 ~ 1.0，默认 1.0）
- UI 入口：**设置面板**里的滑条（托盘菜单里那个已移除）
- 生效范围：**只作用于背景色**，图标和文字始终清晰
- 应用点：`BoxControl.ApplyBoxOpacity()`，读 `MainViewModel.BoxOpacity`，按比例缩放 `BaseCardColor` 的 A 通道
- 持久化：`SettingsViewModel.BoxOpacity` 是**双向代理**（真正状态在 `MainViewModel`，由它 `ScheduleSave` 防抖存盘）

### 一个历史遗留提醒

## 九、踩过的坑

按主题分组。每条：**现象 → 原因 → 做法**。

### 9.1 安装包 / UAC

**① 双击装不上、右键管理员却能装**

- 现象：`Setup was unable to create the directory %TEMP%\is-XXXX.tmp. Error 5`
- 原因：Inno 启动器在**提权之前**就要建解包目录
- 做法：外层套一个带 `requireAdministrator` 清单的启动器（第五章）
- 弯路：改 `PrivilegesRequired` 无效，别再试

**② 报错里的陌生目录名是线索**

- `is-XXXX.tmp` 不是你代码建的，是 Inno 启动器的临时解包目录
- 认出「不认识的目录属于谁」比反复读自己的源码省时间

**③ 换了 AppId 后「程序和功能」出现两条**

- 早前提权安装留下的旧卸载记录用的旧 AppId
- 清理（管理员 PowerShell）：
  ```powershell
  reg delete "HKLM\Software\Microsoft\Windows\CurrentVersion\Uninstall\DesktopBox_is1" /f
  ```

**④ 生成的 `.rc` 报 `RC1004 unexpected end of file`**

- 原因：文件**带 BOM** 或**末尾没有换行**
- 做法：生成 `.rc` 时用无 BOM 的 UTF-8，并保证末尾有 `\n`

**⑤ `PublishInstal​ler` 目录的残留会被打进安装包**

- 原因：`.iss` 用 `publish-installer\*` 通配
- 做法：每次 publish 前**先清空**该目录（`build-installer.ps1` 已处理）

### 9.2 窗口 / 透明

**① 透明像素变成不透明黑**

- 现象：磁贴透明底变成整块黑矩形（实测占窗口区域 97%）
- 原因：子窗口与父窗口之间不做 alpha 混合；子窗口上设 `UsesPerPixelOpacity=true` 还会被 WPF 剥掉 `WS_EX_LAYERED`（建出来 `ex=0x00000080`）
- 做法：**这些窗口必须是顶层窗口**（第七章）
- 一并失败过的：`DwmExtendFrameIntoClientArea`（hr=0x80070057）、`LWA_COLORKEY`（err=87）

**② 忘了开逐像素 alpha**

- 窗口带 `WS_EX_LAYERED`、内容又是透明/半透明的，却没设 `UsesPerPixelOpacity = true` → 那层 layered 的 alpha 从未初始化，透明像素合成成不透明黑
- 历史上犯过两次：桌面层、拖放覆盖层。**守卫测试 `LayeredWindowsWithTransparentContent_EnablePerPixelOpacity` 就是为防这个加的**

**③ 盒子 z 序会随点击变化**

- 这是顶层窗口方案的**已知代价**，不是 bug：点别的窗口会盖住盒子，点盒子才抬起来
- 不要试图用 `HWND_TOPMOST` 解决（会压住普通窗口，用户体验更差）

**④ 半透明底的圆角出现黑角**

- 圆角外是透明像素，会被合成成黑色
- 做法：用 `CreateRoundRectRgn` + `SetWindowRgn` 把窗口本身裁成圆角（`BoxWindow.ApplyRoundedRegion`）
- 细节：椭圆宽高要传**直径**（2×半径），半径按 DPI 缩放才能和 WPF 的圆角对齐；`SetWindowRgn` 成功后区域句柄交给系统，**失败才自己 `DeleteObject`**

### 9.3 右键菜单（原生 shell 扩展）

**① 右键毫无反应**

- 两条独立原因，都要查：
  1. **`AllowSetForegroundWindow` 没调** → helper 的 `SetForegroundWindow` 失败 → `TrackPopupMenuEx` 返回 0
  2. helper 进程卡在 `QueryContextMenu`（第三方扩展导致，实测 0.2 秒 ~ 8 秒以上）
- 做法：启动 helper 前放行前台；等待窗口给到 12 秒；没弹出来就杀掉重试

**② shell COM 调用绝不能放在主进程里**

- **进程内调 `IContextMenu` 会让整个进程 `AccessViolationException` 崩溃**（coreclr `0xc0000005`）
- 这也是为什么菜单必须走**独立的 helper 进程**：崩了也只影响 helper

**③ 就地改名要独立顶层窗**

- 桌面层和盒子窗口都是 `WS_EX_NOACTIVATE` 的，**键盘输入根本到不了它们**
- 做法：`InlineRenameBox` 是一个贴在名字那一行的独立顶层小窗

**④ 合成输入测「属性」时要用鼠标点菜单行，不要用回车**

- 那个回车会被随后弹出的属性框的「确定」按钮吃掉
- 现象：「属性框闪一下就没了」，会查很久

**⑤ 属性框点不开**

- 原因：`ShellExecuteEx(verb="properties")` 是**非阻塞**返回的，属性框挂在调用方窗口/线程上；helper 弹完菜单就退出，把属性框一起带走了
- 做法：helper 弹完先等它出现（第三方属性页首次加载可能几秒，给 25 秒），再泵消息陪到关闭（上限 30 分钟）；**owner 传 `nullptr`**

### 9.4 WPF / XAML

**① 单文件发布后某些 native DLL 找不到**

- 现象：`DllNotFoundException`（`PresentationNative_cor3.dll` / `wpfgfx_cor3.dll` / `D3DCompiler` 等）
- 原因：这些 native dll 默认放在 exe 旁边，被删就崩
- 做法：单文件发布时设 `IncludeNativeLibrariesForSelfExtract=true`；多文件自包含没这问题

**② 小输入框被硬撑到 460x320**

- 原因：`SizeToContent` 在「无边框 + `AllowsTransparency`」上不生效，而且 Wpf.Ui 的 `ControlsDictionary` 给 `Window` 带了最小尺寸 460x320
- 做法：`SizeToContent=Manual` + `MinWidth/MinHeight=0` + 显式 `Width/Height`，Show 之后再用 `SetWindowPos` 按物理像素钉一次

**③ Wpf.Ui 的 hover 动画会致命崩溃**

- 原因：frozen 的主题画刷被 hover 动画改写
- 做法：窗口 `Loaded` 之后调 `Services.WpfUiAnimationGuard.UnfreezeSubtree(this)` 解冻子树（`SettingsWindow.OnLoaded` 里就是这么做的）

**④ `AllowDrop` 不继承**

- 落点判定用「鼠标正下方那个元素」，子元素没开 `AllowDrop` 整块区域就拒绝（禁止光标）
- 做法：把整棵可视化子树逐个打开（`Controls/DropTargets.EnableOnSubtree`）

**⑤ 拖拽效果集必须和落点有交集**

- 条目拖拽原来只给 `Copy`（为拖出到桌面），盒内重排要 `Move` → 效果无交集，系统直接判「禁止」，落点根本收不到
- 做法：给 `Copy | Move`

### 9.5 测试

**① 多测试类并行时随机 `XamlParseException`**

- 见第八章第 4 节，加 `xunit.runner.json` 关并行

**② 单测里绝不能走到 `InputDialog.Inform`**

- 它是 `ShowDialog()`，没人点关闭就把调用线程**永久挂住**，整个测试套件卡死（表现是跑测试超时无输出）
- 做法：ViewModel 里弹窗前判 `Application.Current is not null`，无 UI 上下文只写日志

**③ 大量「读源码做字符串断言」的守卫测试**

- 例如 `window.Should().Contain("settings.hoverExpand")`
- 删功能前先搜 Tests 目录里有没有断言它，否则会莫名其妙红

### 9.6 构建脚本 / 工具链

**① PowerShell 脚本文件（`.ps1` / `.bat`）里绝对不要写中文**

- PS 5.1 按 **ANSI** 读脚本文件 → 语法直接崩
- 要写中文就存成 **UTF-8 with BOM**，或者改用英文注释

**② 不要用 PowerShell 的 `Get-Content` / `Set-Content` 改含中文的源文件**

- 会乱码 + 加 BOM。改文件请用编辑器，或者用 Python 按二进制处理

**③ `Start-Process` 起 GUI 子进程会让外层 shell 一直等到超时**

- 现象：自动化脚本在启动程序后挂死
- 做法：用 `cmd /c start ""`；或者脚本内测完立刻 `Stop-Process` 再返回；更稳的是 `Invoke-CimMethod -ClassName Win32_Process -MethodName Create`（父进程是 WMI，不会挂住调用方）

**④ cmd 括号块里不能展开 `%ProgramFiles(x86)%`**

- 变量名里的 `)` 会被当成块结束符
- 做法：`setlocal enabledelayedexpansion` 之后用 `!VAR!`

**⑤ 编译 .NET 时 NuGet 报 `Value cannot be null (Parameter 'path1')`**

- 原因：自动化环境里缺少 `ProgramFiles` / `ProgramFiles(x86)` / `ProgramData` 环境变量
- 做法：脚本里显式补上这三个变量即可（用户自己的终端不受影响）

### 9.7 git / GitHub

**① `git ls-files` 的中文路径会被转义**

- `core.quotepath=true` 时，git 输出的是 `"\344\275\277..."` 这种转义形式
- 后果：用脚本比对「仓库 vs 某目录」时，中文文件名会误判成「新增/删除」
- 做法：比对脚本里设 `git -c core.quotepath=false ls-files`

**② 中文路径的文件在 `git status --short` 里会显示成转义字符串**

```
 M "\344\275\277\347\224\250\350\257\264\346\230\216.md"
```

**③ GitHub 推送容易 `Recv failure: Connection was reset`**

- 原因：网络链路问题，**不是仓库的问题**
- 做法：重试多次（实测 5~11 次通常会成功）
- 远端可能有别人通过网页改的提交（例如 `Update README.md`）：被拒时**先 `git fetch`**，然后 rebase 保留对方的提交，**不要强推**

**④ `core.autocrlf=true` 会带来「整文件都变了」的假 diff**

- 现象：从另一台电脑拷文件过来，`git status` 里几十个文件显示修改，但 `git diff` 只有十几个是真的
- 原因：行尾（CRLF/LF）差异
- 做法：以 `git diff --stat` 的结果为准；要彻底归一就加一个 `.gitattributes`（`* text=auto eol=lf`）

**⑤ 本机跑不上安装包 ≠ 安装包坏了**

- 自动化/沙箱环境的 `%TEMP%` ACL 可能限制 Inno 初始化（退出码 1 或 4）
- 这类交付物**最终必须在真机上走一遍**，别把沙箱环境的结论当成产品结论

**⑥ fork 仓库默认禁用 GitHub Actions（v1.7.37 发版时卡了很久）**

- 现象：代码推上去了、tag 也打了，但 **Actions 页一个 run 都没有**（API `actions/runs` 返回 `total_count=0`）
- 排查顺序（照这个走能少走弯路）：
  1. `GET /repos/{owner}/{repo}/actions/runs` → 确认是不是真的 0（不是网络/缓存问题）
  2. `GET /repos/{owner}/{repo}/actions/permissions` → 看 `enabled` 是不是 `true`（需要 token，未认证返回 401）
  3. `git ls-tree -r --name-only origin/main | grep workflows` → **确认 workflow 文件真在远端**（本地有 ≠ 推上去了；本地测试读的是工作区文件）
  4. **能用 `workflow_dispatch` 建出 run ⇒ workflow 文件有效**，YAML 问题直接排除
  5. 网页 Actions 页看有没有 "disabled / paused / approval" 提示
- 修法：**Settings → Actions → General → 选 "Allow all actions and reusable workflows" → Save**
  - ⚠️ 该页有**两张独立卡片**（上面 Actions permissions、下面 Artifact and log retention），**各有一个 Save，点错了不生效**
  - ⚠️ 顺带确认 **"Require actions to be pinned to a full-length commit SHA" 不要勾** —— 勾了 `actions/checkout@v4` 这种标签引用会被拒，构建直接红

**⑦ 用 PAT 推 git 必须用 `Basic`，不能用 `Bearer`**

```powershell
$b64 = [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes("x-access-token:$TOKEN"))
git -c "http.https://github.com.extraHeader=Authorization: Basic $b64" push origin main
```

- `Bearer` 对 **REST API** 有效，对 **git 端点无效** → `fatal: Authentication failed`
- token 别写进 remote URL（会留在 `.git/config`），用 `extraHeader` 一次性注入，不落盘

**⑧ 判断 token 有效性：401 ≠ 权限不够**

| 返回 | 含义 |
|---|---|
| **401 Bad credentials** | 凭据本身不被承认（过期 / 没点最后的 Generate / 已被撤销 / 不属于该账号） |
| **403** | 凭据有效但**权限不够**（scope 没勾够） |

- 快速验证：带 token 请求 `GET /rate_limit` —— 这接口**不需要认证**，它返回 401 就说明 token 被拒
- 实践建议：**classic PAT（`ghp_` 开头）+ 勾 `repo` + `workflow`** 最省事；fine-grained 要逐项选仓库和权限，容易漏
- classic 的 40 位 `ghp_` 与 fine-grained 的 93 位 `github_pat_` 都能用，长度/前缀对了不代表有效

**⑨ push/tag 事件在本仓库不产生 run —— 发版用 `workflow_dispatch` 指定 tag ref（关键技巧）**

- 实测：push 到 main（已验证 `c667823..3109392 main -> main`）、创建 tag（已验证 `[new tag]`）**都不产生 run**；而 `workflow_dispatch` **秒级建 run**
- **可用做法**（v1.7.37 实际走通的路径）：

```bash
git tag -a v1.7.37 -m "Release v1.7.37" && git push origin v1.7.37
```
```http
POST /repos/{owner}/{repo}/actions/workflows/build.yml/dispatches
{ "ref": "v1.7.37" }        ← 传 tag 名，不是分支名
```

- 为什么必须传 tag：Release 步骤的条件是 `if: startsWith(github.ref, 'refs/tags/')`。
  **`workflow_dispatch` 会把 `github.ref` 设成你传的 ref** —— 传 `main` 则 Release 步骤被跳过（只出 artifact），传 `v1.7.37` 则 CI **自己建 Release 并上传 `DesktopBox.zip` + `DesktopBoxSetup.exe`**
- 好处：产物由 CI 上传，**不用手动下载 115MB 的 artifact 再传一遍**
- ⚠️ 用 PowerShell 调 API 拼查询串时，`"?x=$ts"` 要写成普通字符串 —— 写成 `` "$url`t=$ts" `` 会把反引号解释成 **TAB**，URL 变成 `/runs/123\t...` → 一串 404

> **已排除的原因（2026-11-22 逐项实测，别再重查一遍）**
>
> | 检查 | 结果 |
> |---|---|
> | `GET .../actions/permissions` | `{"enabled":true,"allowed_actions":"all","sha_pinning_required":false}` ✅ |
> | `GET .../rulesets` | 0 个 |
> | `GET .../branches/main/protection` | 404（无保护规则） |
> | workflow 文件在远端 / tag 内 | `git ls-tree` 确认存在；`state=active` |
> | workflow 是否有效 | `workflow_dispatch` 能建 run ⇒ **YAML 一定有效** |
> | 事件是否真的发出去 | push 验证 `c667823..3109392 main -> main`；tag 验证 `[new tag]` |
> | 有没有卡在"待批准"的 run | 按 `action_required`/`waiting`/`requested`/`queued` 全部为 0 |
> | 按事件过滤 | `push=0` `create=0` `pull_request=0`，只有 `workflow_dispatch=2` |
> | 网页 Actions / workflow 页横幅 | 无 disabled / paused / approval 提示 |
>
> 结论：**GitHub 对本仓库的 push/create 事件就是不建 run，且未暴露任何原因**。
> 可选的后续动作：① 走上面的 `workflow_dispatch` 绕过（已验证）；② 向 GitHub Support 提工单；
> ③ 重建仓库（代价大，非必要不做）。

**⑩ 推送网络抖动的重试要"可验证"**

- 只看 `$LASTEXITCODE -eq 0` 不够：`git push` **成功但没真正推送**时也是 0（例如 tag 远端本来就在 → `Everything up-to-date`）
- 正确做法：**删 tag 后先 `git ls-remote --tags` 确认它真的没了**，再推，并检查输出里有没有 `[new tag]`
- 反面教训：曾把 git 输出丢进 `Out-Null` / 用错过滤条件，导致"以为推了、其实没推"，白等 5 分钟 CI

### 11.1 六个问题的根因与修法

### 11.2 可复用的教训

**① 吞掉系统提示，就必须自己补提示**
`FOF_NOERRORUI` 是为了不弹系统框，但如果代码自己也不提示，用户看到的就是"点了没反应"。**静默 API 一定要配等价的 UI 反馈**（Toast + 日志里带 `rc=`）。

**② 异步填充的属性只能靠绑定驱动**
WPF 里凡是"后台任务稍后写入"的字段（图标路径、下载进度…），UI 必须用 `Binding` + `INotifyPropertyChanged`。命令式 `xxx.Visibility = ...` 只在 DataContext 切换时求值一次，之后永远改不动 —— 这正是"**切个标签就好了**"的典型症状。

**③ 全屏置顶层窗口会截获别的程序的拖放**
`HWND_TOPMOST` + 铺满全屏 = 光标下最顶层的注册 drop target。要给别的程序留路必须按窗口矩形**挖洞**；挖洞要排除自己的进程与桌面层本身，并跳过 `DwmGetWindowAttribute(DWMWA_CLOAKED)` 为真的残留矩形。

**④ 瞬态文件绝不该被收录或画出来**
`~$`、`*.tmp` 寿命只有几秒，收进去只会变成死引用。过滤必须放在**唯一入口**（`DesktopScannerService.ScanDesktop`），桌面层和一键整理同时生效 —— 放两处必然漂移。

**⑤ watcher 事件必须带类型**
只有 `path` 的事件无法区分 新增/删除/改名，三种行为完全不同。带 `Kind` 后才能做：Created→收纳、Deleted→撤引用、Renamed→改路径。

**⑥ 启动清理要"窄"，别顺手删设计上要保留的东西**
第一版把所有失效引用都删了，**被测试当场抓到**：既定设计是"失效引用保留、手动『刷新失效图标』清理"。改成只清**瞬态名**残留后 354/354 全绿。→ **动手清理前先问：这是 bug 还是既定行为？**

**⑦ 全局状态要有测试隔离钩子**
`GlobalDragTracker` 的 1.5 秒拖动窗口是全局的，一次 `MarkDragEnd` 会污染后续用例。加 `Reset()` 并在测试 `finally` 里调用。

**⑧ 先分清"产品问题"还是"环境问题"**
单文件 exe 报 `Failed to create extraction directory ... error 5`，看着像产品坏了；把 exe **移出工作区**立刻正常 —— 是沙箱限制工作区内 exe 建目录。同理 `loose=0` 一度怀疑过滤器把桌面项全滤掉，**用全新配置实测 `loose=278`** 才排除。**结论必须来自对照实验，不要从现象直接下判断。**

**⑨ 每条行为都要有"真机证据"，不能只靠单测**
单测锁逻辑，真机锁链路。本次留下的三条证据：

```
[Desktop.Cleanup] 启动清理临时文件引用 2 条            ← 问题6 的 ~$ 残留 2→0，条目 290→288
[Desktop.Watch] Created → [Desktop.AutoCollect] ... tab=cat.docs   ← 问题4 自动收纳
[Desktop.Watch] Deleted → [Desktop.Watch] 撤掉失效引用 1 条        ← 问题6b 删除清引用
```

**⑩ 需要真实交互的修复，必须人工验收后才算闭环**

有三项无法用单测覆盖，只能真机点一遍 —— **2026-11-22 逐项确认全部通过**：

### 11.4 v1.7.38 补丁：桌面框选的诊断与自愈

**现象**：桌面上无法拉框选择文件；**重启程序后恢复**。

**诊断方法（这套流程值得复用）**：框选这条链路原本**一行日志都没有**，只能靠猜。于是在 4 个关键点埋探针 —— 每道守卫拒绝时都记下**该点真实窗口的类名**：

```
[DesktopLayer.Marquee] 跳过:该点不是桌面 (1458,18) class=HwndWrapper[DesktopBox;;…]   ← 点在盒子窗口里
[DesktopLayer.Marquee] 跳过:该点不是桌面 (1700,1059) class=ToolbarWindow32            ← 任务栏
[DesktopLayer.Marquee] 跳过:该点不是桌面 (1406,845) class=Chrome_RenderWidgetHostHWND  ← 别的程序
[DesktopLayer.Marquee] 开始 (1566,267) ctrl=False
[DesktopLayer.Marquee] 结束 rect=[…] 磁贴=2 命中=2
[DesktopLayer.Select] 选中 2 项,首项=…\南通表(3).xlsx
```

结果：**框选本身是通的**（成功选中 2 项），所有拒绝都是正当的（`IsDesktopWindowAt` 只认
`SHELLDLL_DefView / Progman / WorkerW / SysListView32`，其余一律不拉框）。

**根因判断**：历史那段没有日志，无法回溯；但"重启就好"是**状态卡死的典型信号** ——
`_marqueeSelecting` 若在上一次拉框没收尾时卡在 `true`，第一道守卫会永久拦掉后续所有框选。

**修法（自愈，而不是记日志后 `return` 放弃）**：

```csharp
if (_marqueeSelecting)
{
    // 新的一次左键按下本身就证明上一次已经结束了 → 重置，别永久卡住
    _marqueeSelecting = false;
    _mouseHook.TrackingDrag = false;
    if (_regionExpanded) { _regionExpanded = false; ApplyRegion(full: false); }
}
```

区域也要一起收回来 —— 否则 `WindowFromPoint` 会一直返回我们自己，`IsDesktopWindowAt` 照样过不去。

**教训**：

1. **"重启就好了" = 状态卡死的指纹**。凡是守卫用的布尔状态，都要问一句：它卡在 `true` 谁来解？
   答案必须是"下一次输入自动解开"，不能是"用户重启"。
2. **诊断探针要留着**。`WindowClassAt` 这条日志现在是框选问题的唯一线索，删掉它下次又只能靠猜。
3. **拒绝也要有理由**。守卫 `return` 时静默放弃是最难查的一类问题 —— 至少把"拒绝原因 + 现场"记下来。

### 11.5 待办设计：盒内图片显示缩略图（**暂缓，2026-11-22 讨论后决定暂不修改**）

**诉求**：盒子里的图片能显示实际内容缩略图，一眼看出是哪张照片。

**现状（已探明）**：
- 现在拿的是**壳类型图标**：`SHGetFileInfo + SHGFI_ICON`，jpg/tif/pdf 全是类型图标，看不出内容
- 缓存 `icons/<sha12(路径+mtime)>.png`，改文件会自动重取 ✓；现有 2187 个 / 2MB / 平均 0.9KB
- 磁贴图标区 `IconBox 44×44`、`Image 40×40`，默认 `Stretch=Uniform`（不会压扁）
- 当前盒内真正的图片只有 **5 个**（2 `.tif` + 1 `.png` + 1 `.jpg` + 1 无扩展名截图），另有 18 个 `.ico`（本就该显示图标，不需要缩略图）

**三条路线**：

| | A. WPF 自己解码 | B. Shell 缩略图 API | **C. 混合（推荐）** |
|---|---|---|---|
| 做法 | `BitmapImage` + `DecodePixelWidth=96` | `IShellItemImageFactory::GetImage` | B 优先 → A 回退 → 现壳图标兜底 |
| 格式 | 内置 jpg/png/bmp/gif/tiff；webp 要插件、heic 看系统 codec | 与资源管理器一致，装了 codec 的都行（heic/webp、装了 PS 的 .psd） | 覆盖最全 |
| **EXIF 方向** | ⚠️ 要自己读 EXIF 旋转，手机照片不转就是横的 | ✅ 系统自动处理 | ✅ 由 B 解决 |
| 线程 | 纯托管无坑 | ⚠️ COM 必须 STA —— **`StaTaskRunner` 现成**（`SHGetImageList` 的 MTA 坑已趟过） | 复用现成 |

**待拍板的 5 个问题**：
1. **范围** —— 只做图片（建议白名单 `.jpg .jpeg .png .bmp .gif .tif .tiff .webp .heic`），还是顺带视频首帧/PDF 首页？（后两者要解码，慢一个数量级）
2. **尺寸** —— 显示 40×40，建议存 **96×96**（2x 屏清晰，单张 3–6KB，1500 张 ≈ 8MB）
3. **缓存** —— 沿用现有 key（路径+mtime）即可；要不要限总量/LRU？建议先不限，加日志观察
4. **时机** —— 复用现有后台提取，但图片解码慢（大图 50–200ms）→ 降采样解码 + 并发度 2
5. **失败回退** —— 损坏图/不支持格式回退现有壳图标，**绝不白屏**（这条不用讨论，直接做）

**预估工作量**：`IconExtractorService` 加图片分支 + 新增 `ShellThumbnail`（COM/STA，约 80 行）+ 回退链 + 约 10 条测试 ≈ **半天**。

**恢复讨论时**：从"待拍板的 5 个问题"问起即可，前三条路线的取舍已经写清楚了。
